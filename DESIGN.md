# Big Deck Optimization — Design

A Slay the Spire 2 mod that removes lag when playing with huge decks (200+ cards).

Target game version: **v0.107.1** (Godot 4, C# / .NET 9, game logic in `sts2.dll`).

## Goal

- **Success criterion:** no visible frame drop or lag during combat with **1000 cards**.
- Comfort target 500 cards; must not collapse at **2000+**.
- In scope: combat (draw/shuffle/end of turn), deck/draw/discard pile views, combat start, out-of-combat screens listing the deck (rewards, shop, campfire upgrade/remove), **co-op** (the original lag report is a 4-player co-op run).
- Out of scope: the game's own memory leaks / degradation over a long run. The mod itself must not leak (checked before each release: `docs/RELEASE.md`).

## Hard constraints

1. **No patch may change game state.** Up to v0.3.0 the manifest said `affects_gameplay: false` (one co-op player with the mod, the others without). Since v0.4.0 it says `true`: the game only lets players with the same gameplay mods (id and version) join, because a player without the mod falls tens of seconds behind at every combat start and the game drops the actions that reach a player still starting a combat (Step J, co-op). Results must still be bit-identical with vanilla: peers can have different switches, a patch can turn itself off after an error, and `bdopt off` must give the unmodified game.
2. **Bit-identical.** Every patch on a logic path (hook dispatch, per-card recalculation, checksum, serialization) must give exactly the vanilla result, and is checked against vanilla: in the bench (`bdperf`) and, for the checksum, live (`SnapshotVerifier`).
3. **Never crash.**
   - At startup, each patch is applied in isolation; a missing target only disables that patch (logged).
   - At runtime, an exception inside a patch disables it for the session and falls back to vanilla.
   - An optimization backs off when another mod patches its target (`PatchSafety`).

## Optimization categories

- **(a) Invisible — always on.** Everything shipped so far is in this category.
- **(b) Visual concessions — "Auto" mode.** Enabled by default only above a deck-size threshold (default 300, configurable), each one toggleable. Examples: capped shuffle animation, faster draw animations, per-card VFX cut. Not started.
- **(c) Gameplay logic changes — never.**

### 16,800 cards + 736 relics (2026-10-23, `solo-16k`, `solo-16k-trace`)

Double the reference size (its cards 18x, relics 2x), release-like timings: idle combat smooth (no frame over 100 ms in
10 s), combat start 10.2 s, plays and end of turn at ~8 fps (frames 110-190 ms), ~30% of action time in GC pauses
(`gcstat`: e.g. 4 plays 7.6 s with 2.3 s of GC; mostly gen1 collections, ~50 ms each). Trace: Limitless'
`RecalculateCardValues` patch re-serializes every stacked enchantment after each action (`MultiEnchantment.SetSerializableCards`,
~13% of the main thread here: ~13,000 enchanted cards since the reference run's 735 are copied 18x), with BaseLib's
extended save data (`ConditionalWeakTable` entry per `ToSerializable`) on top; per-frame rich-text effects (`RichTextGold`/`RichTextSine`) ~16%.

Tried and dropped: skipping BaseLib's empty extended-data entries (identical checksum and save packet, but no clear gain
in an A/B over 4 turns: plays 7.6/8.0 s off vs 5.2/6.1 s on with different cards, end of turn 5.5/4.7 vs 6.3/5.0 s).
The table cost in the trace is mostly GC triggered there. A real fix would be in Limitless (re-serialize only changed
cards); its serialized state is checksummed, so it stays untouched here.

## Technical choices

- Harmony runtime patching (`0Harmony.dll` ships with the game). C# .NET 9 class library referencing `sts2.dll`, `GodotSharp.dll`, `0Harmony.dll` from the game folder (not copied).
- Decompile with ILSpy (`ilspycmd`) into `/decompiled` — **gitignored, never committed** (MegaCrit and other mod authors' code). The public repo contains only our patches.
- No dependency. BaseLib is optional (v0.2.3; a manifest dependency + Workshop required item in v0.2.1-v0.2.2, dropped because some players report BaseLib broken and the game then refused to load this mod too): it only hosts the settings menu, in a separate `BigDeckOptimization.Menu.dll` loaded once BaseLib is loaded. Config files must go to `%APPDATA%/SlayTheSpire2/mod_configs` (BaseLib: `BigDeckOptimization.cfg`), **never as `.json` in the mod folder** (see modding facts).
- Compatibility: **must** work with Limitless and BetterSpire2; best effort with SpeedX, CampfireTrade, BaseLib. Patches are prefixes/postfixes/finalizers that only skip the original inside well-defined read-only scopes.
- Language: English only for v1.

## Game modding facts (v0.107.1)

- Mods load from `<game dir>/mods/` (recursive) and Steam Workshop (app 2868840). Each mod: `<Id>.json` manifest + `<Id>.dll` (+ optional `.pck`).
- **Every `.json` file in a mod folder is read as a manifest** → the build disables `deps.json` generation.
- Manifest fields: `id`, `name`, `author`, `description`, `version`, `has_pck`, `has_dll`, `dependencies` (`[{id, min_version}]`), `affects_gameplay` (**defaults to `true`** — must be set explicitly), `min_game_version`.
- Entry point: a class with `[ModInitializer("MethodName")]` (static method); without it the game calls `Harmony.PatchAll` on the assembly.
- Multiplayer: only mods with `affects_gameplay: true` are included in the gameplay mod list compared between players (`ModManager`).
- Console commands: subclass `AbstractConsoleCmd`; the dev console auto-discovers subtypes in mods. Debug commands are allowed whenever the game runs modded. `IsNetworked` commands go through the action queue in multiplayer and run on **every** peer (`ConsoleCmdGameAction`), so they must be deterministic and every peer needs the command.
- Console key: `` ` ``, `'`, `*` or `^` (AZERTY: `*` or `^`).
- Logs: `%APPDATA%/SlayTheSpire2/logs/` — **only the last few sessions are kept**; copy them right after a session worth analyzing.
- Run history: `%APPDATA%/SlayTheSpire2/steam/<steamid>/modded/profileN/saves/history/*.run` (JSON, full decks and relics per player).
- Game beta v0.111.0 (`public-beta` branch, 2026-10-26) changes met so far (decompiled in `decompiled/sts2-beta/`): `AbstractModel.ModifyDamage*` and `Hook.ModifyDamageInternal` take a `CardPlay? cardPlay`; `CardPile.RemoveInternal` calls a new `InvokeCardRemoved`; `SavedPropertiesTypeCache` merged into `ModelIdSerializationCache` (same `GetJsonPropertiesForType`); `Mod.assembly` became `Mod.assemblies`; `CardSelectCmd.PushSelector(selector, localOnly = false)` (a local-only selector answers only the local player's choices, synchronized like a human's; the global one answers every player's choices locally); `Rng(ulong seed)` instead of `Rng(uint, int)`; `StartRunLobby.Players` holds `StartRunLobbyPlayer`; `CombatManager.StartTurn` takes a `CombatTurnState`; `CombatManager.SetupPlayerTurn` takes a `CombatTurnState` (state and cancellation token from it); `Hook.BeforeTurnEnd`/`AfterTurnEnd` renamed `BeforeSideTurnEnd`/`AfterSideTurnEnd`; new hook `BeforeCombatRewardOffered`; `Hook.AfterBlockBroken` passes a choice context and the breaker; `HookPlayerChoiceContext`'s constructor finds the owner through a new `GetOwner` (no `combatState.Players[0]` throw for a null state) and `AfterDeath` uses `NonCombat` actions outside combat; a hook added near the top of `Hook` renumbered every compiler-generated `<Hook>d__N` below it (same code: fingerprints ignore that numbering since v0.7.0). The game sets every player's `PlayerCombatState.Phase` to `None` outside their turn.

## Findings

### Phase 0 (2026-10-21): the co-op checksum

- Singleplayer with a 791-card deck: no lag except at combat start. The co-op run (4 players, 791-card deck incl. 736 Squeeze / 735 enchanted, a teammate with 189 relics) lagged for **every** player during the whole combat.
- The post-action checksum (`ChecksumTracker`, **multiplayer only**) snapshots the full state (`NetFullCombatState.FromRun`) on every peer after every action. Measured: **92 ms and 64 MB allocated per checksum** with 802 combat cards; serialize + hash is only 0.6 ms.
- Root cause: `CombatState.IterateHookListeners()` allocates a fresh list of all listeners (every card, enchantment, relic, power, mod subscriber…) on each call. The snapshot calls it 3× per card (keywords, energy cost, late energy cost): O(cards²).
- Fix: `ListenerCache` (snapshot scope) + hook filter (now `HookFilter`) → **94 ms → 3.8 ms per checksum (x24.8), bit-identical**.
- Each peer computes its own checksum: a player only gets the gain if they have the mod.

### Phase 2 (2026-10-21): dotnet-trace, singleplayer, 935 cards + 368 relics

- Combat setup itself is cheap: `SetUpCombat` 66 ms (card cloning 38 ms).
- **After every action**, `CombatStateTracker.CallCombatStateChangedDeferred` takes 80–100 ms (356 ms at combat start): `RecalculateCardValues` (every enchantment, incl. Limitless multi-enchantments) + hand refresh (`NCard.UpdateVisuals`, `CanPlay` ×5 per card). Every hook call rebuilds the listener list → O(cards²) again. Fix: `ListenerCache` refresh scopes. **Not measured in game yet.**
- Relic bar: every `NButton` gets every input event via `_Input` (only used for drag-cancel while pressed): 368 Godot→C# calls per mouse move. Fix: `IdleButtonInput`. **Not measured in game yet.**
- `CombatState.Players` allocates a list (LINQ) on each call; `IterateHookListeners` calls it every time (720 ms of the trace). Covered inside cache scopes only.
- **Measured in game (2026-10-21, singleplayer, 2830 combat cards + 370 relics)**, all identical to vanilla:
  - checksum: vanilla 1723 ms → cache 422 ms → cache+filter **40 ms** (x42.8). Relics make vanilla far worse (1.7 s vs 94 ms with 2 relics).
  - post-action refresh (`bdperf refresh`): 80 ms → **21 ms** (x3.9).
  - relic bar input: 2333 ms → 46 ms of a 60 s trace.
- Remaining in the refresh (second trace): Limitless `MultiEnchantment.RecalculateValues` over every card (~27%), `CanPlay` → BaseLib's `HasEnoughResourcesFor` patch and `Hook.ShouldPlay` still walk the whole (cached) listener list per hand card. Relic hover tooltips (vanilla, created on hover) are the rest of the relic bar cost.
- Third trace + `bdperf combatstart` (945 cards + 368 relics): refresh 21.7 → 6.1 ms; enemy intents (`RunState.IterateHookListeners`, which also walks the whole permanent deck) now covered. Combat start is ~5.9 s wall clock but almost all of it is relic animations/waits (AfterRoomEntered ~2.9 s ≈ 6 StoneCracker × 0.5 s, BeforeCombatStart ~0.7 s, first turn ~1.6 s); assets + scene + SetUpCombat ≈ 100–170 ms; only one long frame (99–208 ms, first render of the room = the "black screen"). Shortening waits would change timing, which SpeedX itself flags as a co-op desync risk → only as an opt-in (b) concession.
- Not addressed: `RichTextSine` / `RichTextGold` custom text effects (~10% of the main thread, per character per frame, mostly Godot→C# wrapper creation, unavoidable from C#).

### Step D (2026-10-22): card grids (deck view), singleplayer, 945-card deck + 370 relics, Limitless

- `NCardGrid` is already virtualized by the game (sliding window of ~6 rows of pooled holders), on every grid screen (deck view, piles, card selection). No virtualization needed.
- 4 traces of the same gestures (scroll, each sort twice, inspect). Before: scrolling 45 ms per row (max 275 ms), half of it Limitless' `UpdateEnchantmentVisuals` (`Node.Duplicate` of every tab on every render, 9.1 s of 90 s); a sort click 30–114 ms (`List.IndexOf` tie-break per comparison, culture string compare, cost).
- After `EnchantmentTabReuse` + `GridSortCache`: duplicates 9.1 s → 0.2 s, sort ≤ 4 ms (bench 24–39 ms → 2.4 ms, identical orders); scrolling 34 ms per row.
- Remaining scroll cost is vanilla per-card rendering (~7 ms per card: title/type/description autosize, energy/star cost visuals), the same for any deck size.
- `ListenerCache` was dropping its cache on every `CardModel.Enchantment` set, including Limitless' ownerless enchantment storage cards rebuilt while rendering every enchanted card: now only owned cards invalidate. Combat refresh with Limitless: 23.6 → 2.0 ms (x11.7, was x3.9).
- Tried and removed: listener scopes around `NCardGrid.AssignCardsToRow`/`InitGrid` (BaseLib's type plaque walks every run listener per rendered card): no measurable gain, materializing the list costs as much as the walks it saves.
- Vanilla, deck-size independent: `NodePool.Free` → `DisconnectIncomingAndOutgoingSignals` walks every node of every freed card and lists all its signals (Godot dictionaries), 60–340 ms on each grid init (open, sort); the actual disconnects are ~6 ms. `PoolSignalScan`: 12.3 s → 5.9 s over comparable gestures (avg 118 → 47 ms per grid init, worst ~280 ms). What remains is reading connections that do exist (engine/internal ones) only for `DisconnectSignal` to skip them: unavoidable without changing behavior.
- Harmony on `NodePool<NCard>` methods does not reach the shared code reference-type instantiations run (`NodePool`1[__Canon]`): patch non-generic entry points instead.
- Logs: a singleplayer session log is ~34 KB, nothing repeated at volume: no log reduction needed.

### Step G (2026-10-23): unattended 8,425-card sessions (`AutoTest`), singleplayer, 368 relics, all Workshop mods of the reference setup

Scenario: reference run imported once with relics, then its cards 8 more times (8,425 deck cards ≈ the friends' 8,274-card co-op combat), `fight CULTISTS_NORMAL` with 999,999-HP enemies. Measured with `PerfProbe` (per-method times + long frames) and dotnet-trace.

- Combat start (vanilla, mod off): ~31 s. Relic effects play one after the other with their animation waits (`AfterRoomEntered` ~6 s, `BeforeCombatStart`, first turn), each costing more because frames are slow. With 3,312 relics (relics imported 9×) it was 140 s. `FastCombatStart` (Instant-mode waits until the first play phase, 50+ relics): 23.7 → 10.4 s; same relic results (Vulnerable 7 / Weak 6 / block 37 / player powers identical with fast, normal and mod off).
- First turn: one 6 s frame = `SetupPlayerTurn`'s Innate filter on the draw pile: `c.Keywords` → `Hook.ModifyKeywordsInCombat` → full listener walk per card (O(n²)). In a refresh scope (`ExtraScopes`): 6,497 → 12 ms, same cards (checked against vanilla in Debug).
- Every frame in combat ~100–300 ms: BetterSpire2's `DamageTracker.Recalculate` (4×/s, `Hook.ModifyDamage` per enemy/intent outside any scope) was 22% of all CPU. In a refresh scope + listener lists reused across refresh scopes while nothing changed.
- `CardModel.Pile` (= `_owner.Piles.FirstOrDefault(p => p.Cards.Contains(this))`) is read through `CardModel.CombatState` everywhere: ~780k calls during one combat start, ~5 µs each with 8,000 cards. `PileIndex` answers in O(1). First version updated the index in postfixes and was caught by the exhaustive check: `AddInternal`/`RemoveInternal` raise `CardAdded`/`ContentsChanged` (whose listeners read `card.Pile`) before postfixes run → updated in prefixes, undone by a finalizer if the original throws.
- Combat end: `NetCombatCardDb.OnPileContentsChanged` re-walked a whole pile per removed card while `Player.AfterCombatEnd` clears the piles: 597 → 1 ms with `CardDbScan`; end-of-combat hitch 1,225 → 545 ms. Pile counters re-fitted their label 8,500 times (`PileCounterBatch`).
- Remaining (not addressed): per-frame rich-text effects (`RichTextGold`/`RichTextSine` custom FX, ~20% of idle CPU, mostly Godot→C# call overhead), hooks during actions outside scopes (each walks every listener), `SaveRun` ~100–160 ms after combat, rewards generation ~100 ms, ~40 ms GC per frame with 8k cards.
- `bdperf refresh`/`checksum` run vanilla first: at 8k cards they take minutes (the game looks frozen). Use them at ≤3k cards.
- With the scopes above, BetterSpire2's recalculation was dominated by `Creature.IsHittable` → `Hook.ShouldAllowHitting` (every listener per call): now filtered by `HookFilter`; filtered lists are kept while their (reused) source list is the same. `PatchSafety.IsPatchedByOthers` (`Harmony.GetPatchInfo`) was 1.3 s per 20 s of idle when called per scope: results cached 2 s.
- Release-like numbers (bench re-checks off, Normal speed, 8,425 cards + 368 relics): combat start 31 s (vanilla) → 4.4 s; idle combat frames no longer over 100 ms; card play ~0.46 s wall (36 ms CPU); end of turn ~0.3 s; combat end hitch ~1.2 s → 263 ms. Apotheosis on 8,400 cards: 0.4–0.7 s.
- Journey (`tools/autotest/scenarios/journey-8k.txt`, 8,425 cards, 368 relics, Workshop mods): combat, shop (~0.75 s hitch on entering), rest site (~0.2 s), elite start 2.5 s, The Kin boss start 3.7 s, boss killed → end-of-combat hitch 192 ms. Rooms (`rooms-8k`): treasure/event/map instant, deck view opens in ~50 ms.
- Not worth it: `CombatState.IterateHookListeners` outside scopes (each hook during actions walks every listener) is ~45% `Contains` per model, ~20% BaseLib subscribers, ~10% list growth: a mirror would gain ~10% at the heart of game logic. Only an action-wide verified cache would really help (future work, high care). After-combat save ~300 ms (240 ms Steam Cloud write) and card rewards ~80 ms are inherent.
- ~10,300 cards (`solo-10k`): combat start 4.9 s, card plays 0.3–0.5 s (Apotheosis on 10,300 cards 1.5 s), end turn → next turn 2.1 s, combat end hitch 0.36 s.
- Co-op turn transition (`coopturn`, host traced, ~8,400 combat cards, Workshop mods): ~9.6–9.9 s from ending the turn to playing again, the CPU busy all along. Biggest single cost ~1.6 s: **Limitless `MultiEnchantment.SetSerializableCards`**, called not only by `RecalculateValues`/`OnEnchant` but inside pure calculations (`EnchantBlockAdditive`/`Multiplicative`, damage equivalents): every block/damage computation re-serializes all inner cards (`CardModel.ToSerializable`, through BaseLib's extended save data). Not changed here: the serialized list is checksummed in co-op, so skipping refreshes could diverge from peers running Limitless without this mod; an upstream fix in Limitless (serialize only when the inner cards change) would remove it. Then hook walks during actions ~2.1 s, `QueueFreeSafely` ~0.6 s, `MegaLabel.AdjustFontSize` ~0.4 s, the Debug probe ~0.7 s (not in Release). Both instances share one PC (CPU/GPU), so this is pessimistic for real co-op.
- Local co-op (2 instances, ~3,750 cards each): two combats, every turn's state identical on both peers, 30 checksums (4 verified vs vanilla), 0 mismatch, no divergence. But `SnapshotVerifier`'s vanilla rebuild took ~9 s per verification at that size (first 3 actions + 1 in 25 froze ~9 s): verifications are now budgeted to ≤1% of play time (the first two extra checks only while a check costs < 250 ms), and skipped entirely above 1,000 combat cards or after a check over 1 s (user's choice 2026-10-23: no multi-second freeze; the earlier sessions never found a mismatch).

### Step J (2026-10-23): the 59 pile-scanning cards (`pile-cards-on/off/small/trace`)

- Scenario: 8,425 cards + 368 relics, No Draw applied (`NO_DRAW_POWER`; the earlier `NO_DRAW` id didn't exist), each card made free (`playcard X free`, X costs keep `setenergy 5`) and played alone; Grand Finale (needs an empty draw pile) and Regret (unplayable curse) left out. `CARDPLAY` lines log every play: exactly the 59 scenario cards manually, plus 12 auto-plays from Beat Down, Cascade, Catastrophe, Havoc and Uproar, identical in every session.
- Sum of per-card times: mod off 65.2 s, v0.3.0 patches 28.6 s, now 17.0 s; same cards with only the relics (`pile-cards-small`): 6.9 s. CHECKSUM/STATE/CARDPLAY lines identical on/off. Almost every card cost ~400 ms more at 8,400 cards than with a small deck: a per-action cost, not per-card scans.
- Trace of those 42 s (v0.3.0 patches): Limitless `SetSerializableCards` 17.9 s, almost all in `ConditionalWeakTable.AddOrUpdate` from BaseLib's extended save data postfixes (~7,000 multi-enchanted cards × inner cards × 2 entries per `RecalculateCardValues`; dependent handles also weigh on every GC). `LimitlessReserialize`: 6.3 million lists kept, 0 rebuilt, 0 Debug mismatch. Its remaining cost (~5 s per session) is the comparison itself, mostly BaseLib's save getters, which must run to stay exact.
- `FastListeners` filters walking every pile entry with a type lookup each: 4,663 uncached walks (filters tracking ExecutionFinished subscribers) + ~1,000 rebuilds per session → shared `PileSnapshot`. Tracking subscriptions instead was rejected here (the event accessors could be inlined, and a missed change would drop an `InvokeExecutionFinished`); Step K does it with safety nets.
- Inside ListenerCache scopes, hooks materialized every listener (~30,000) after each state change, e.g. for BetterSpire2's `IsHittable` 4×/s: `HookSkip` now also filters there.
- `HookFilter` built its per-hook lists by materializing every listener (~30,000) once per state version, then filtering them, mostly for the few hand cards refreshed after each action: now each hook's list comes from FastListeners' filtered walk (listeners outside piles + the cached pile entries overriding that hook), same objects and order, cached per scope and version (Debug: 1 build in 32 compared with the materialized way). Tried and dropped: letting the first calls after a change go to HookSkip's walk instead (the cost only moved).
- Allocations (`run.ps1 -TraceProfile gc-verbose`, AllocationTick stacks read with a TraceEvent tool): 2.4 GB per 10 s of turns, 78% from `LimitlessReserialize`'s own comparison (a new `ExtendedSaveData` and its dictionaries per inner card). Now one reused data object (dictionaries emptied, then BaseLib's registered getters run into it, as its constructor does) and lookups by registered id: 0.75 GB per 10 s, 14 GCs instead of 49, GC pauses ~100 ms per turn instead of ~280. What remains of it is BaseLib's own getter (`DirectModifiers(card).Select(...).ToList()`), left as is.
- 59 cards: 28.6 s (v0.3.0) -> 14.0 s. 5 turns + combat end, all on (`hookskip-on`) vs all off (`turns-off`): identical. Turn ~3.0 s (v0.3.0) -> ~1.6 s, plays 83–108 fps (45–55), end of turn 53–60 fps (20–25).
- Audit fixes: inside `CardPile.RandomizeOrderInternal` the game hands the pile's own list to `ModifyShuffleOrder` listeners, which reorder it in place with no bump, so FastListeners' caches (segments since v0.3.0, snapshots now) are bypassed there (`shuffle-on/off`: 6 turns with reshuffles, identical); `ListenerCache.RunVanilla` (the snapshot verifier's and the bench's vanilla reference) now also turns HookSkip off, which now runs inside the checksum scope; the deck snapshot no longer keeps the deck alive after a run; `LimitlessReserialize` treats empty collections as equal only for arrays and `System.Collections.Generic` types. Regression set: `pile-cards-on/off`, `hookskip-on`/`turns-off`, `shuffle-on/off`, `listeners-8k` (identical listeners), `hover-tips-8k`, `fast-start-check` (PileIndex checking every answer).
- Left: keepSubscribed walks (cache misses reading each entry's subscriber field), UI (`NCard.UpdateVisuals`, `NHandCardHolder.UpdateCard`, orb visuals' `ModifyOrbValue`), materialization for hooks HookSkip doesn't cover inside scopes, BaseLib's getter allocations.

### Step K (2026-10-24): copying thousands of cards (`clone-*`, `reflections-*`, `coopclone`)

- Campfire clone with Limitless' stacked Clone (`Patch_OnSelect.Replacement`: one `CardPileCmd.Add` per Clone stack) and Bing Bong (each relic copies every card added to the deck, `clonedBy` stops the recursion): the reference run imported twice = 1,880 cards with 1,520 Clone stacks and 4 Bing Bongs, so 7,600 adds (1,880 -> 9,480 cards); at 16,840 cards, 68,400 adds (-> 85,240). The user's trace (v0.4.0): >90 s, 94% in `CardPileCmd.Add`, of which FastListeners' deck walks rebuilt the whole deck snapshot and segments after every add (each `AddInternal` bumps `PileVersion`): O(n²).
- FastListeners: an add that appends a card at the end of a pile with nothing else changing between its two bumps is journaled (`_appends`: consecutive versions, cleared by any other change); a snapshot whose piles only got appends to their last pile since its version appends the new entries (`PileSnapshot.CatchUp`, same `Generation`), and each segment extends itself from the snapshot entries it hasn't consumed. Enchantment/affliction setters no longer bump for a card in no pile (`PileIndex.InNoPile`): a fresh clone gets its enchantment before it's added, which used to invalidate everything.
- Filters keeping ExecutionFinished subscribers (AfterCardChangedPiles, ModifyCardBeingAddedToDeck and most "after" hooks) are now cached too: `SubscriptionVersion` is bumped around `add_/remove_ExecutionFinished` (fingerprinted with `AfterCloned`, the only other writer, on fresh clones) and around the game's only subscriber's own methods (`NPlayerHand.AfterCardsSelected` / `OnSelectModeSourceFinished`), whatever the JIT did with the accessors there (Harmony 2.4 disables inlining of patched methods; the game isn't ReadyToRun; tier-0 code never inlines). Every build checks a cached hit of these filters against the live subscriber fields at most once every 2 s (one walk: constant cost); a difference stops caching them for the session.
- `RelicFlashMerge`: the screen went black during the clone (and the game crashed at 16k -> 85k): ~9,000 `NVfxParticleSystem` (GPU particles) over the relic bar, one per Bing Bong flash in the same frame, overflowing D3D12's per-frame descriptor heap ("Cannot bind uniform set because there's not enough room in the current frame's RESOURCES descriptor heap"). Now 27,126 -> 8,898 nodes, 0 renderer errors.
- Card-add previews are left exactly vanilla: the game caps them at ~51 on screen (`CardCmd.PreviewInternal`, a flying card keeps its place until it lands); in vanilla the clone freezes the game, then one wave of 51 flies (`clone-visual-vanilla`: all optimizations off except the flash merge, previews sampled 4×/s). A queue replaying the dropped previews (a stream of up to ~1,000) was tried and removed at the user's request.
- Second trace (16,840 -> 85,240): `List.IndexOf` 11 s = `RunState.ContainsCard` (`_allCards.Contains`; the card just created is last: now `LastIndexOf`, same comparer, same answer) + `CardPile.AddInternal`'s duplicate check (`Cards.Contains`; a PileIndex transpiler answers false when the index counted this add as the card's only pile, i.e. it was in no pile, which is also every combat move since the game removes the card first; 1 in `VerifyEvery` checked); `PatchSafety.IsPatchedByOthers` took a lock per hook call (now lock-free reads); the journaled-append `ConditionalWeakTable` (replaced by PileIndex). Pitfall: Harmony re-runs transpilers each time a method is re-patched, so the transpiler's "replaced once" flag must be local.
- Results: 16,840 -> 85,240 cards 33.9 s (first fix) -> 13.8 s (release-like: `bdperf probe off`, `bdperf segments verify off`), 89 fps afterwards; 1,880 -> 9,480: 15.7 s -> 1.7 s; three clones in a row from 1,880: 9,480 (1.7 s), 55,080 (16.5 s), 328,680 cards (6.6 min, then 122 fps at the campfire; a fourth is out of reach). Reflections/Shatter (copies the deck card by card with a 0.1 s / 0.2 s wait each, none at Instant): Instant 31.1 s -> 4.8 s (1,880 -> 11,285); Fast ~195 s both ways (the waits), 144 -> 180 fps during it, frames over 33 ms 206 -> 26.

### v0.7.0 audit (2026-10-27): crashes, change detection, performance

Every place this mod's code runs inside the game was reviewed for what an exception there would do:

- Harmony prefixes/postfixes on game methods: each catches its own errors and falls back (added for the per-card-move prefixes of PileIndex and CardDbScan, which relied on `PatchGuard` alone: the move that threw would still have failed once).
- Lazily run code (iterators run by the caller, async hooks): FastListeners' pile-entry cache and mod-subscriber snapshot, and HookSkip's per-call checks, fall back to the vanilla walk on an error (an exception in an async state machine never reaches `PatchGuard`). The subscriber walk's reflected fields are resolved and type-checked at load: a renamed field used to be found null only inside every walk.
- Transpilers: Harmony reruns them whenever another mod patches the same method later, so they never throw (HookSkip's no longer assumes its table entry exists).
- Event handlers: the `AssemblyLoad` handlers run inside other assemblies' loads and never throw (unknown = conservative answer); the menu DLL is load-checked like a patch before BaseLib's screen can run its code, and its text update can't break that screen.
- Missing members at load: the patch is skipped (update), never left half-applied.

### Co-op with a player without the mod (2026-10-24, verified)

Local co-op, ~3,750 cards per player, Workshop mods, the client's mod off (`bdopt off`) as the stand-in for a player without it:
- `coopvanilla` (both play at once): divergence at the first action, with v0.4.0 and with v0.3.0 alike. The state dumps (the game logs both sides' states on a divergence) show the actions ran in a different order.
- `coopsolo1` (only the modded host plays): divergence. The unmodded client took 33 s to start the combat; the host's first plays reached it meanwhile and were dropped (`ActionQueueSet`: "currently cancelling all combat actions"; Limitless logs these too: "combat action(s) were rejected since the last combat start (healthy sessions show 0 or 1)").
- `coopsolo2` (only the modded client plays): no divergence but a frozen run: the unmodded host dropped the client's plays and its end of turn, so the enemy turn never came.
- `coop` (both modded) and `coopoff` (both off): no divergence.

Cause: the game's own handling of actions received during a combat start, made near certain by a speed gap of tens of seconds (combat start ~4 s with the mod, 30+ s without; the faster combat start option alone skips ~70 s of waits). Hence `affects_gameplay: true` and `FastCombatStart` always on in co-op (a player with that option off would start ~70 s late). Verified: `coop-required.ps1` (client with this mod disabled) gets the game's "Mods mismatch: the host has mods we don't have: BigDeckOptimization-v0.4.0" and can't join; `coopfast` (both modded, the client's fast start off) skips the waits on both sides, identical states, no rejected action. Two modded players on very different PCs can still meet it, as in vanilla, with a much smaller window.

## Implemented patches (`src/BigDeckOptimization/Patches`)

Safety nets around every patch (v0.6.1, after v0.6.0 broke combat on game beta v0.111.0, where `AbstractModel.ModifyDamageCap` gained a parameter: HookFilter's prefix couldn't be JIT-compiled, so it threw on its first call before its `Enabled` check and try/catch, and every damage calculation threw even with the mod switched off):

- **Load check** (`PatchSafety.RequireResolvable`, ~25 ms for all patches): before applying a patch, `ModEntry.TryApply` resolves every member and type its class uses (nested types, lambdas and state machines included) and checks they are accessible. A member removed, changed or made private skips that patch (vanilla). `RuntimeHelpers.PrepareMethod` would also catch other JIT failures, but methods compiled that way skip tiered compilation: turns at 32k cards were ~2% slower.
- **Rollback** (`PatchGuard`): an Apply that fails halfway has the patches it already installed removed.
- **Runtime guard** (`PatchGuard`): every patched method gets a void finalizer (Harmony then rethrows unchanged; inlined null check, no measurable cost). An exception leaving a patched method through a frame of a patch class faults that patch (off for the session, menu says so) and removes all its Harmony patches on the next frame. Test: `faultprobe` (scenario `guard-checks`).
- **Fingerprints of what each patch relies on** (v0.7.0, `MethodFingerprint`): IL with tokens resolved to names, the compiler's numbering of generated members ignored (`<Hook>d__42`, display classes, lambdas: it shifts when the game adds a member above, with the same code), and the code of the generated methods it uses included (lambdas, local functions, state machines: a changed lambda changes its user's fingerprint). Besides the mirrored methods themselves, patches pin what their reasoning assumes: HookSkip and HookFilter the `AbstractModel` defaults they skip (a default that stops being a no-op leaves its hooks vanilla), HookSkip the choice-context helpers (`HookPlayerChoiceContext` constructor/`GetOwner`/`AssignTaskAndWaitForPauseOrCompletion`/`WaitForCompletion`, `PushModel`/`PopModel`, `InvokeExecutionFinished`) for the hooks using them. Patches whose caches are kept up to date by watching some methods check that no other code may change what those methods guard (`PatchSafety.RequireFieldWriters`: assignments, mutating calls, the collection passed to a method taking a mutable one; new readers don't count; a new writer would change no fingerprint): `CardPile._cards` (ListenerCache, PileIndex, FastListeners), `Player._relics` and `_potionSlots` (ListenerCache), `AbstractModel.ExecutionFinished` (FastListeners' subscriber tracking). `tools/fpdiff fieldusers <dir> <type> <field> [--writers]` lists them. HookSkip also backs off a hook whose state machine another mod patches (a transpiler there could add a walk that this patch's redirect would filter), except BaseLib 3.4.7's AfterEnergyReset and AfterCardPlayed transpilers (they only make the hook first await a method of BaseLib's own; transpilers and their injector `AsyncMethodCall.Create` fingerprinted). Until v0.6.4 this wasn't checked: those two BaseLib transpilers ran with the redirect (harmless, see above), any other would have gone unnoticed. A fingerprint from another game version is accepted when that code was checked to behave the same, so one DLL keeps the patch on both: per version where a generator re-validates it (HookSkip's table: `tools/hookskip/classify.py` classifies every supported version on its own code), by hand otherwise (`EquivalentFingerprints.cs`, each entry saying what changed: beta v0.111 `CardPile.RemoveInternal`, `SavedProperties.FromInternal`, `SetupPlayerTurn`). `tools/fpdiff review <old> <new>` lists every fingerprinted method that changed between two versions with its IL and C# diff, the members it newly calls (with their code, and whether they changed) and renames; `tools/autotest/mutations.ps1` checks the reactions in game. Beta v0.111 with v0.7.0: nothing left vanilla (147 hooks), A/B `ab-2k-off/on` identical on both versions.
- **Errors inside async hooks** (v0.7.0): most hooks run in async state machines, where an exception only faults the hook's task and never leaves the patched method, so `PatchGuard` can't see it. The code of this mod running there falls back by itself: FastListeners' own pile-entry cache, on an exception, turns FastListeners off (HookSkip with it: its option lists both faults) and the walk adds every pile entry like vanilla (a superset whose extra entries keep the no-op defaults), so the hook completes normally; HookSkip's per-call checks turn HookSkip off and walk vanilla. Test: `bdperf fault piles`, scenarios `guard-async-on` vs `guard-async-ref` (same checksums). A method, field or type missing at load is logged as a skipped patch (update), not an error.
- **Off at start** (`ModEntry.StartedOff`): when BaseLib's saved settings have the whole mod off when the game starts, no patch is applied (test tooling only): switching it off and restarting always gives the unmodified game, whatever the bug. Turning it back on then takes effect at the next start (bdopt and the menu say so). Scenario `started-off` (run with `"Enabled": "False"` in the cfg).

Changes to existing patches (2026-10-30, Step O):

- `FastListeners`: affliction changes of a card in a pile bump `AfflictionVersion` instead of `PileVersion` when the old and new affliction types are both known (types are recorded the first time they are seen, by the setter or a snapshot rebuild; a change involving a new type bumps `PileVersion` as before). - `PileIndex`: the owner's piles are read without `Player.Piles`' `Concat` iterator (two allocations per `CardModel.Pile` call) while that getter has its v0.107.1/v0.111 code (`_runPiles` field, combat `AllPiles`); otherwise through the getter as before.
- `HookFilter`: `ForCombat`/`ForRun` look the walked list up before creating the walk lambdas (two closures per call, even on cache hits: ~70 MB per 13 s of co-op plays at 4,100 cards).
- `ListenerCache`: materialized listener lists are sized from the previous count (thousands of entries grown by doubling allocated twice as much, the last arrays on the large object heap).
- `Settings`: parts of an option (`LimitlessRecalcSkip`, `SnapshotCardReuse`, `TextPoolReuse`) turn themselves off alone after an error (`Part`), and don't make their option unavailable when not applied.

## Console commands

Public (`src/BigDeckOptimization/Commands`, in every build):

- `bdopt [on|off]` — every optimization on/off at runtime (vanilla when off), or the state of each one (incl. patches skipped or self-disabled). Local, safe in co-op.
- `bdopt <option> on|off` — one optimization (keys: `coop_checksum`, `combat_refresh`, `hook_filter`, `relic_input`, `relic_flashes`, `grid_sort`, `grid_pool`, `pile_lookup`, `card_ids`, `pile_counters`, `fast_combat_start`, `limitless_tabs`, `listeners`, `hook_skip`, `hover_tips`, `limitless_saves`, `card_type_line`); `bdopt fast_combat_start_relics <0-100>` sets the fast combat start's relic threshold (BaseLib slider). Saved in BaseLib's mod configuration. Never re-enables a patch that turned itself off after an error.

## Test tooling (`src/BigDeckOptimization/Bench`, Debug builds only: excluded from Release by the csproj, `BENCH` symbol)

- `bigdeck <count> [card-id] [seed]` — fill the deck up to count (one card, or random from the character pool). Networked + seeded (seed 0 default): usable in co-op if **every** player has the mod.
- `bigdeck relics <count> [relic-id] [seed]` — add relics (character + shared pools), no obtain effects. Networked.
- `bigdeck import <file.run|shared-name> [all|i|i,j] [cards|relics|all] [hash]` — exact decks (upgrades, enchantments) and relics from a run history file, added like a save load (no obtain/card-added hooks). Players can be merged. In co-op: only bare names from the shared folder `user://bigdeck` (`%APPDATA%\SlayTheSpire2\bigdeck`), and the SHA-256 prefix from `bigdeck hash <name>` is required, so every peer provably reads the same file.
- `bigdeck tank [hp]` — sets every living enemy's max and current HP (default 1,000,000) for long perf-test combats. Networked.
- `bigdeck hash <shared-name>` — prints the SHA-256 prefix of a shared run file (each peer prints its own).
- Caps: deck ≤ 5000, ≤ 1000 relics per command (any peer can issue networked commands).
- `bdperf checksum [n]` — vanilla vs cache vs cache+filter checksum cost, checks identical checksums.
- `bdperf refresh [n]` — vanilla vs cached post-action refresh (enchantments + hand), checks the game state is identical afterwards.
- `bdperf verify [off|sample|all]` — live verification mode and counters (snapshots, verified, mismatches), patch on/off state. `all` costs a vanilla snapshot per action: singleplayer debugging only.
- `bdperf grid [cards]` — deck view sort orders (vanilla vs cached, identical orders), enchantment tab rendering on cards spread over the deck (vanilla vs reuse, identical tab state), and freeing grid holders to the pool (vanilla vs scan, identical remaining connections). Bench timings of rendering/freeing are far below in-game ones (hidden container, no GC pressure): use them for identity, traces for gains. UI only, usable anywhere in a run.
- `bdperf combatstart` — wall-clock breakdown of the last combat start (phases, GC pauses, longest frames). `checksum` and `refresh` refuse to run in real co-op.
- `bdperf opt on|off` — all optimizations on/off at runtime for an A/B comparison in the same session (safe in co-op: both paths give identical results).
- `bdperf probe [reset|log|on|off|hitch <ms>]` — `PerfProbe`: per-method calls/total/max (async: also wall time to completion) for ~25 deck-size-sensitive methods, sampled callers of `CardModel.Pile`, and every frame over the threshold (100 ms) logged with the probes that ran in it.
- `bdperf pile [verify <n>]` — `CardModel.Pile` for every card: index vs vanilla answers and timings; `verify 1` checks every live answer against vanilla.
- `bdperf plaque [n]` — BaseLib's card type line for the first n cards of the local piles, TypePlaqueSkip off then on: same `LocString` object for every card, and the times.
- Local co-op (`tools/autotest/coop.ps1`, see its README): two instances launched directly with `--force-steam off` (no Steam, so only the local `mods` folder loads: vanilla + this mod; each instance has its own data folder `user://default/<net id>`, the first launch needs the mods warning accepted once per folder), `--fastmp host_standard` / `--fastmp join --clientId 1001` (ENet on 127.0.0.1:33771), `--log-file <path>` for separate logs, and `--bdtest <script>`. Script `mplobby <CHARACTER> [players]` picks and readies up; console commands go through the action queue in co-op. The test runner fixes the `fight` command's clock-based encounter seed (else peers desync) and answers card choices identically on both peers (deterministic selector, which also bypasses choice syncing). Imports of runs played with mods cap upgrade levels / skip unknown cards and relics. Fur Coat throws on `fight` before visiting the map (`CurrentMapPoint` null) and the combat never starts: the runner skips it when there is no map point. `-WithMods` copies the user's enabled Workshop mods into `<game>/mods_STEAMTEST` (read without Steam) and always deletes it: a normal launch reads it too.
- `AutoTest` — unattended sessions (launchers and scenarios in `tools/autotest`): start the game through Steam with `-applaunch 2868840 --bdtest <script>` (a direct exe launch fails Steam init). ### Lesson (stress trace 2, 2026-10-21)

Per-handler scopes cost more than they saved: each outermost scope rebuilt and re-filtered ~12k listeners for one or two hook calls (filter 7.3 s + rebuild 2.8 s per 60 s). Scopes must be coarse (one per refresh) and the filter single-pass.

### Stress results (2026-10-21, singleplayer, ~4,690 cards + ~1,840 relics = 5x the reference run)

| Build | Refreshes / 60 s | Avg per refresh | `bdperf refresh` |
|---|---|---|---|
| cache only | 670 | 27.4 ms | — |
| + HookFilter, per-handler scopes | 625 | 29.8 ms | x5.9 (hand only) |
| + single dispatch scope, single-pass filter | 798 | 16.9 ms | 152 → 14 ms, x10.7 |

Remaining per refresh (~12 ms inside the scope): run listener materialization ~2.3 ms, filter ~1.6 ms, Limitless enchantment visuals, CardCostHelper energy/star cost loops. Out of scope: gameplay hooks (damage, HP loss, after-damage...) ~20 ms per hit at this load — caching them needs lazy per-item `Contains` semantics and a dedicated verifier (desync risk), deferred to v0.2. Reusing lists across refreshes was rejected: BaseLib card modifiers can change between refreshes without a hook we can track.
